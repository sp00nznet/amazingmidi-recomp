# Architecture

Three parts, all in one 32-bit process (`build\amazingmidirecomp.exe`):

| Part | Where | Owns |
|---|---|---|
| The lifted program | `src/recomp/gen/` (generated by `run_lift.py`, gitignored) | every function of `amazingmidi.exe` 1.70 as C, one `recomp_XXXX.c` per 400 functions, plus `recomp_dispatch.c` for indirect calls |
| The host | `src/runtime/host.c` | argument parsing, mapping the original image, and the few identity calls (below) |
| The runtime | pcrecomp `runtime/native32`, `runtime/recomp32` (from `..\pcrecomp`) | the image loader, import binding, and the bridge between lifted code and real Windows |

## Data flow

1. `disasm32.py` reads `work\amazingmidi.exe` and writes `work\functions.json`
   (3,232 functions).
2. `run_lift.py` lifts every catalogued function, plus the seeds in
   `seeds/run_seeds.json`, to C. It refuses any exe whose PE stamp is not
   `0x3F5249AC` (1.70).
3. At run time the host maps `game\amazingmidi.exe` at its own base
   (`0x00400000`; the host links at `0x60000000` so that range is free), binds
   its 372 imports (365 to real Windows DLLs, 7 shimmed), and enters the lifted
   entry point `0x0040CAB3`. Only the original's data and resources are used
   from the mapped image; none of its code runs.

## Why the host shims identity calls

MFC loads its menus, dialogs and icons from the module handle it gets from
`GetModuleHandleA(NULL)`. Unshimmed, that is the host exe, which has none of
them. So the host answers `GetModuleHandleA(NULL)`, `GetModuleFileNameA` and
`GetCommandLineA` as if it were `amazingmidi.exe`. Nothing else in the
program needed a fix.

## Why one seed

`0x0041D5F1` is reached only through a function pointer, so the catalog's
call-graph walk never finds it. The first run reported it unresolved; it is
seeded in `seeds/run_seeds.json` (addresses only, no code).
